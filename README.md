# SmartWork

**Рабочее место для малого сервиса.** Один владелец, команда сотрудников, несколько «столов» — отдельных рабочих контуров под точку или направление. Внутри стола: календарь, очередь заказов, задачи, справочники и сводная аналитика. Проект изначально задуман как учебная платформа с полноценным стеком и возможностью демонстрации на защите: здесь виден и продукт, и инженерия под капотом.

---

## Зачем это существует

Маленькая парикмахерская или груминг-салон не нуждается в «ERP на все случаи жизни», но ей нужен порядок: кто на смене, что в очереди, какие услуги и клиенты в справочниках, как выглядит день в календаре. SmartWork собирает это в одном веб-интерфейсе и даёт владельцу инструменты управления персоналом и столами, а сотруднику — понятную зону работы только по тем столам, куда его пустили.

Тип стола можно выбрать из предустановок (например, барбершоп или груминг): под них подтягиваются шаблоны справочников и примеры карточек — не с пустого листа, а с осмысленной заготовкой.

---

## Что внутри: короткий обзор возможностей

**Учётные записи и доступ.** Регистрация, подтверждение, восстановление пароля, приглашения сотрудников. Роли разделены: владелец управляет столами и кадрами, сотрудник видит только назначенные ему столы.

**Панель владельца.** Список столов, создание стола с подтверждением по коду (защита от случайных действий), блок сотрудников и привязка их к столам, общая аналитика по столам, настройки профиля и уведомлений, экран подписки как часть продуктовой логики.

**Рабочее пространство стола** — отдельный маршрут с вкладками:

- **Календарь** — слоты и планирование по времени.
- **Задачи** — статусы в духе «новая / в ожидании / выполнена», чтобы видеть поток работ.
- **Справочники** — услуги, клиенты, для груминга ещё и питомцы; у записей есть структурированные поля (payload), а не только пара строк текста.
- **Аналитика** — сводки и мини-графики по столу; часть возможностей может быть связана с бонусами подписки (например, разблокировка расширенной аналитики).
- **Настройки стола** — параметры вроде формата времени, начала недели, рабочих часов.

**Очередь заказов** на бэкенде ведётся как отдельная сущность со статусом «в очереди» — это основа для отображения загрузки и для дальнейшего развития сценариев приёма заказов.

**Инфраструктура под почту.** В составе Docker-стека есть почтовый контейнер (MailHog): письма не теряются в пустоту при разработке — их можно открыть в веб-интерфейсе и показать проверяющему, что цепочка «событие → письмо» реально отрабатывает.

## Архитектура: как устроен проект

Система разделена на клиент, API и данные. Связь асинхронная там, где это важно для масштабирования и отзывчивости.

| Слой | Технологии |
|------|------------|
| Клиент | **Angular 19**, маршруты с ленивой подгрузкой страниц, **PrimeNG** и темы Prime |
| API | **FastAPI**, **Pydantic**, JWT, CORS |
| Данные | **PostgreSQL 16**, **SQLAlchemy 2** (async), **Alembic** в репозитории |
| Кэш и сессии | **Redis** (например, коды подтверждения при создании стола) |
| Контейнеры | **Docker Compose**: БД, Redis, почта, backend, статическая отдача фронта через nginx в образе `web` |

Документация REST доступна из коробки: **Swagger** по адресу `/docs` и **ReDoc** по `/redoc` на сервисе API. Точка **GET `/health`** отвечает простым статусом готовности — удобно для оркестрации и healthcheck в Compose.

## Модель предметной области (сжато)

- **Пользователь** — логин, профиль (ФИО, телефон, аватар, должность и др.), роль, для сотрудников — привязка к владельцу (`owner_id`).
- **Стол** — название, описание, предустановка отрасли, настройки времени и недели, владелец.
- **Участник стола** — связь пользователя со столом (не владелец, но имеет доступ).
- **Заказы, задачи, слоты календаря** — привязаны к столу, поддерживают сценарии очереди и планирования.
- **Справочники и элементы** — типизированные `kind`, расширяемый **JSONB payload** для полей карточки.
- **Бонусы стола** — условные «покупки» вроде дополнительных слотов справочников или разблокировки аналитики.

Такая схема позволяет и демонстрировать нормализованную модель на дипломе, и наращивать фичи без ломки всего API.

## Запуск для демонстрации и разработки

**Вариант «всё в Docker».** В корне репозитория лежит `docker-compose.yml`. После настройки `.env` (или переменных окружения) поднимаются база, Redis, почта, API и веб-интерфейс. Порты по умолчанию: API **8000**, веб **80**, PostgreSQL **5432**, Redis **6379**, веб-интерфейс MailHog **8025**.

**Локальная разработка фронтенда.** В каталоге `frontend` — стандартный цикл Angular CLI: `npm install`, затем `ng serve` и работа на **http://localhost:4200**. Убедитесь, что CORS в API включает origin вашего дев-сервера (в `backend` это настраивается через `CORS_ORIGINS`).

**Бэкенд отдельно.** Каталог `backend`: виртуальное окружение Python, `pip install -r requirements.txt`, переменные `DATABASE_URL`, `REDIS_URL`, `JWT_SECRET_KEY` и запуск через uvicorn (см. `Dockerfile` в `backend` как эталон команды).

Для отладки писем в Docker-сборке SMTP указывает на сервис `mail` — письма попадают в MailHog, а не к реальному провайдеру.

## Надёжность и развитие

Проект позиционируется в коде как **заготовка API для дипломного проекта** — это честно: часть сценариев (подписка, бонусы) заложена как продуктовая обвязка, которую можно углублять или упрощать под требования вуза. При этом уже есть: разделение ролей, многопользовательский доступ к столам, асинхронная работа с БД, миграции, контейнеризация и открытая спецификация API.

Если смотреть на SmartWork глазами комиссии: это не «статичный макет», а связка клиент — сервер — хранилище — вспомогательные сервисы, которую можно развернуть, показать в браузере и сослаться на автоматически сгенерированную документацию эндпоинтов.
